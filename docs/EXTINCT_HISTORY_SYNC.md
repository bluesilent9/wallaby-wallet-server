# Extinct history discovery — Server Build 16 / Agent Build 97

The Server is a signalling coordinator. It neither fetches nor forwards history records, raw transactions, proofs or labels for this update. Agents transfer and verify those over their authenticated direct SSH channel using the existing signed wallet transfer review.

An Agent advertises the read-only wallet RPC `wallaby_extinct_summary`. It accepts no parameters (`[]` or `{}`) and only exact wallet endpoints `Wallaby Extinct` or `Extinct`. Its returned object has exactly: `version` (1), `chain` (`main`), `addresses` and `transactions` (integer counts), `address_hash`, `transaction_hash`, `label_hash`, `history_complete` (boolean), and `digest`. All hashes are lowercase SHA256 hex. `digest` hashes the canonical object excluding itself. No node tip appears in the comparison digest, so new blocks alone do not create new offers.

Normal low-priority wallet inventory collects this optional small summary once per inventory refresh. Failure of the summary alone does not erase normal wallet inventory. Discovery requires current, unambiguous connected Agents, fresh inventories tied to their current connections and exactly one identifiable Extinct archive per Agent. An unknown or incomplete summary cannot authorise a transfer or establish that a source archive is complete.

If summaries disagree, the Server offers the existing `wallet_transfer` request for the public address-only Extinct container even if the destination already holds all its addresses. No new executable request kind or history payload is sent through the Server. An internal `history_sync` record binds the observed peer fingerprints for deduplication and profile validation; it is not transfer authority. Both peers must advertise the new summary RPC. Source selection favours higher address counts, then transaction counts and local coverage, solely to pick a useful first comparison direction. Missing local scan coverage does not prevent offering an existing native snapshot: current Agents independently review and validate that snapshot without claiming it is a local historical scan. Agents must independently verify all facts.

The same observed mismatch is offered only once, including after denial or failure; it does not automatically retry a failed operation. Executing transfers, recovery, restoration and deletion defer another comparison for that pair. A v3 public preserve-only request (`phase=preserve`, `delete_wallet=false`) waiting for missing history does not block the history update it needs. Completed operations and their frozen approvals remain recorded. After a merge, a fresh summary disagreement can offer a reverse comparison to preserve records unique to either peer. Explicit retry after local reconciliation retains history-purpose metadata and does not mistake existing addresses for proof of complete history.

Existing local deny lists, pre-pairing public offers, signed preview, pairing and local approval gates remain. Intentional multisig signer accounts are unaffected. The Agents retain their safeguards against silently making an active wallet extinct, discarding recipient history or overwriting conflicting LOST labels. An empty extinction request queue does not establish matching history.

## Whole-archive scope and delayed outcomes

A pending subset invitation is replaced by a separately reviewed full-container invitation when a fresh, unambiguous loaded source contains additional addresses. Frozen proposals, signed previews, approvals and outcomes on the old invitation are retained. The replacement has a new transfer identity and preview challenge and copies no approval. It remains a public offer until local permissions, pairing and readiness allow review. The known old subset is withdrawn rather than repeatedly offered as the full archive.

A completed subset transfer does not prove that the full archive is current. Fresh summaries can therefore offer the missing native history. A late verified completion of a strict public subset does not suppress the separately reviewed larger update; late failure, denial or uncertain recovery continues to block automatic replacement. The receiver merges rather than deleting its existing Extinct wallet.

Pruning alone does not mark this native public-history comparison as requiring a blockchain redownload. Agents decide whether their actual approved records and coverage satisfy the operation; the Server never fabricates a scan receipt. Intentional signer accounts and ordinary active-wallet download checks are unchanged.
